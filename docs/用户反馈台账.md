## 3. 移动端反馈分析

证据来自源码检查与 v0.9 验收文档，没有把静态分析记为手机实机复现。

| 问题 | 项目依据 | 建议与验收 |
| --- | --- | --- |
| 触屏缺少下令前预览 | `src/battle-ui.js` 的抬指立即执行；路线、能源、伤害与反击主要通过 hover；`battle.css` 小屏隐藏预览详情 | 触屏“点目标预览→明确确认”；显示 AP、路线、能源与反击，拖动／多指不得执行命令；保持观察权限，不能泄露迷雾 |
| 手势不完整 | `bindBoard` 仅保留一个 drag 状态，无多指 pointerId 管理与双指缩放 | 单指平移、双指缩放；旋转、取消、后台中断都清理手势；100 次拖动与双指测试无误下令 |
| 窄屏信息过密 | 760px 断点仍并排单位栏与 148px 回合栏，部分字体 8—9px；镜头初始宽度固定 | 底部可收起单位面板、独立结束回合按钮、小地图按需展开；主要文字建议 ≥14px，常用按钮触控区 ≥44×44 CSS px |
| 大地图与新立绘可能增加成本 | `src/ui.js` 重建 app，最多 919 格；新图如一次加载全部大立绘会增加首次加载 | 同设备测基线后再优化；地图用 Q 版／缩略资源，图鉴大图按需载入，记录首屏与内存 |
| 长局与中断续玩 | 现有自动保存、回合快照、快速 AI 和自动部署已存在 | 先验证 Android Chrome／iOS Safari 的切后台、旋转、恢复与本地保存。不得重复结算回合收入 |
| 可能需要机制修改 | 尚无玩家单局时长与退出节点样本 | 第二阶段评估独立短局地图、少单位预设与较少参与方；不直接削去 AP、能源、反击或占领规则 |

建议真实设备覆盖 360／390／412px 竖屏及横屏；手机端主流程不依赖键盘、右键或悬停。现有 Node／内存 DOM 验证不能代替屏幕布局与手势验收。

44×44 是本项目建议采用的易触控目标，与 [WCAG 2.2 的增强目标尺寸（2.5.5，AAA）](https://www.w3.org/TR/WCAG22/#target-size-enhanced)相同，不把它误称为 AA 的最低要求。地图远景应提供自动放大或明确目标列表，不能只扩大重叠点击区。[MDN 双指手势示例](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events/Pinch_zoom_gestures)可作为 Pointer Events 多指状态管理的实现参考。

移动端缺少的证据：设备型号、系统／浏览器版本、访问方式、具体页面与操作、是否能稳定复现、卡顿还是误触。客服追问这些信息即可，不先要求玩家提供账号或其他无关资料。

## 5. 营销建议与验证

核心定位草稿：“指挥机装少女，协同陆海空，夺回雾海航路。”对应的可验证产品卖点是美少女单位、不同兵种特性与六边形回合协同。

在概念阶段，优先展示同一型号的“精美立绘→Q 版→战术特性”对照。第一批可用前哨、棱镜、浪锋：展示轻装守备、主战推进和两栖登陆。材料明确标注概念稿，不用现阶段无法证明的游玩画面或上线日期。

验证改版方向时分别邀请现有战略玩家与潜在二次元玩家。记录喜欢的角色／机装、兵种识别混淆、对 Q 版的接受度，以及在同一可玩样例中继续游玩的意愿。预设问题保持中性，例如“你觉得这个角色是什么兵种？”而非“是不是比旧版更好看？”。喜欢立绘不等于留存提高，不能据少量选择推断商业收益。

待可玩样例完成后，再比较相同场景的新旧版：首次进入、首次有效下令、兵种判断、一次短局完成与反馈。若新美术明显增加误认或加载时间，先改轮廓和资源规格，再扩大宣传。

## 6. 后续记录格式

每条新反馈记录：编号／日期／原话／来源／版本／设备与访问方式／场景与复现步骤／实际影响／证据／建议方案／优先级／责任岗位／状态／验收结果／对外口径。

状态依次为：新收集→已归类→待复现或待评审→已排期→实现中→待验证→已上线→回访。无法复现与暂缓要记录理由；合并重复项保留原来源。开发角色与排期未指定前写“建议岗位／待排期”，不编造负责人、截止日期或反馈次数。
